# LightningIndexer Decode Update 测试报告

## 测试配置

数据来自 `runlog/01.txt` 的最新一轮测试。

- Batch size：`24`
- 请求长度范围：`32768..65536`
- 实际采样范围：`33258..64667`
- Dtype：`bf16`
- Cache size：`12288`
- 计时方式：NPU Event
- Warmup：`3`
- Iterations：`100`

本轮实际请求长度为：

```text
[61651, 40425, 33258, 38708, 35056, 38268, 39218, 56009,
 48287, 33910, 34787, 33806, 55449, 64503, 63147, 42503,
 38750, 44767, 40266, 33726, 64667, 49140, 36999, 63301]
```

每次调用 update 算子前均恢复独立的 `cache_slots` 副本；恢复操作在计时区间之外。

## 正确性结果

| Miss count 范围 | LightningIndexerDecodeUpdate |
| --- | --- |
| 0 | 通过 |
| 50..200 | 通过 |
| 200..500 | 通过 |
| 0..2048 | 通过 |

每个 batch row 均通过以下检查：

- `topk_index` 与 `LightningIndexerDecode` reference 的 multiset 一致。
- `topk_slots` 全部位于 `[0, cache_size)`。
- 更新后 `cache_slots[b, topk_index] == topk_slots`。
- miss token 位于输出前缀，hit token 位于输出后缀。
- `miss_count` 同时等于目标 miss 数和旧 cache 中的实际 miss 数。
- 更新后每行仍有 `cache_size` 个有效 slot，且值集合恰好为 `0..cache_size-1`。

正式算子对应的 4 组 correctness 测试均通过，未出现异常或断言失败。

## 性能结果

单位：`μs`。表中算子时延为日志记录的 NPU Event 平均时延减去 `20 μs` 固定下发开销。

`额外时延 = Update 算子时延 - 同一次脚本中的 LightningIndexerDecode 时延`。

| Miss count 范围 | Baseline | Update 算子 | Update 额外时延 |
| --- | ---: | ---: | ---: |
| 0 | 363 | 380 | 17 |
| 50..200 | 369 | 403 | 34 |
| 200..500 | 364 | 425 | 61 |
| 0..2048 | 370 | 537 | 167 |
